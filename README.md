# AKS Harness CD Pilot

A runnable Python CLI agent for preparing and operating **Harness CD on an existing Azure Kubernetes Service cluster**. Generates reviewable manifests, validates release configuration, verifies the selected AKS context, and requires `--yes` for remote mutations. Each repository works independently.

This is an evaluation/staging deployment kit. It does not provision AKS, migrate data, or change DNS/production traffic. Customer Azure/Harness authentication, networking and authorization must be configured before live deployment. See [verification boundaries](docs/VERIFICATION.md).

## Install and prepare

Requires Python 3.10+, Git. Live AKS commands additionally require Azure CLI, kubectl, kubelogin, an authenticated Azure session, and network access to your AKS API. Docker is needed only to build/test the included sample.

```sh
git clone https://github.com/THEJANAIDU/aks-harness-pilot.git
cd aks-harness-pilot
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
cp config.example.json config.json
```

Edit `config.json` with your subscription UUID, resource group, cluster, explicit kube context, dedicated namespace and application name. Use a **real image digest** (`registry/repo@sha256:...`) and a **full Git commit SHA** containing your application manifests at `deploy/app`. Example zero digests/SHAs and `REPLACE_ME` values are deliberately rejected. Secrets do not belong in this file. The CLI rejects unknown configuration fields.

```sh
python agent.py validate --config config.json
python agent.py render --config config.json --output generated
```

Rendering is offline, creates a new directory, and never overwrites existing output. Review all generated YAML before executing. `app/application.yaml` is a two-replica HTTP application on port 8080, with probes, resource limits, non-root UID 10001, read-only root filesystem and a ClusterIP Service. It assumes an image compatible with those settings; use the included sample or adapt the source generator/tests for your application.

## Publish the sample release

The manual **Build sample image** GitHub workflow publishes the included sample to GHCR and reports its immutable digest. Make the package readable by AKS (public sample package or preconfigured pull credentials); repository visibility does not automatically make its GHCR package public. For private images, have your platform team supply an image pull mechanism and adapt the manifest; credentials are never generated by this kit.

1. Build/publish the sample, or publish `sample/` with your approved registry tooling. Put the resulting digest in `config.json`.
2. Set `revision` temporarily to an existing real commit to render the application files. Rendering does not verify remote commit contents.
3. Copy `generated/app/` to `deploy/app/` in your chosen Git repository, review, commit and push it.
4. Set `repo_url` to that repository and `revision` to the pushed commit's **40-character SHA**. Render again to a new directory. Do not use the temporary render for deployment.
5. Verify that the exact commit contains `deploy/app/application.yaml` with the intended image digest. Use the deployment instructions below.

Release manifests and the agent may live in the same repository or separate repositories. The pinned commit must already exist before deployment; the CLI does not push Git changes.

## Connect to Azure

```sh
az login
az aks get-credentials --subscription SUBSCRIPTION_UUID --resource-group AKS_RG --name AKS_NAME --file ./pilot.kubeconfig
export KUBECONFIG="$PWD/pilot.kubeconfig"
kubelogin convert-kubeconfig -l azurecli
kubectl config get-contexts
python agent.py doctor --config config.json
```

Set the exact context name in config. The CLI checks AKS metadata against the kubeconfig server and checks API readiness. It never requests `--admin` credentials or silently switches the cluster. See [identity and permission setup](docs/IDENTITY.md).

## Set up Harness and deploy

This kit targets Harness SaaS `https://app.harness.io`. It requires your account identifier, org/project identifiers, existing pipeline/input-set identifiers, and an official non-root `harness/delegate` image with a real supported **tag and digest**. Obtain the current image from your account's delegate install screen; the kit does not invent a version or token. Regional/self-managed Harness endpoints require an explicit reviewed source change.

1. In Harness create/select your org/project and a project-scoped service account. Grant only view/execute access to this pipeline and its referenced environment/service/input set. Keep its key in `HARNESS_API_KEY`, provided through your secret manager.
2. In the rendered output, review and apply `platform/` as a platform administrator: `kubectl --context CONTEXT apply -f generated/platform/`. This creates `harness-delegate`, its service account, and a Role/RoleBinding in the target application namespace. It grants no cluster role and no Secret reads.
3. Create a delegate token in Harness for this project/account. Store it as Secret `harness-delegate-token`, key `token`, in namespace `harness-delegate`, using your secret manager or `kubectl create secret generic ... --from-file=token=/secure/path/token`. Protect the file and remove it after secure import. Do not put tokens on the CLI or in Git; Kubernetes Secrets need encryption at rest and restricted administrator access.
4. Run `python agent.py bootstrap --config config.json --yes`. It verifies the Secret exists, installs the pinned delegate and waits for pod readiness. In Harness verify the delegate named/tagged **aks-harness** is **Connected**. Pod readiness alone does not prove Harness connectivity. Allow outbound HTTPS/WSS to Harness and access to Git, registries and the Kubernetes API.
5. Create project connector **aks_incluster** (Kubernetes, use credentials of a specific delegate / inherit service account; selector `aks-harness`). Test its namespace connectivity. Do not accept generated default cluster-admin RBAC from an installation wizard. Create GitHub **account-type** connector **aks_git**, URL `https://github.com`, with a read-only GitHub App/token secret for your source repository, and selector `aks-harness`. Test that connector too.
6. Import `harness/environment.yaml`, `service.yaml`, `infrastructure.yaml`, then `pipeline.yaml` into the corresponding Harness entities/YAML editors. The service fetches `deploy/app` at your pinned commit. The pipeline targets `aks_staging` / `aks_namespace`, with rolling deployment and automatic stage rollback on failure. Validate/save the pipeline in your account: server validation depends on your licensed features and existing connectors.
7. Create and save a real input set for that pipeline (e.g. `staging`), resolving all runtime inputs. Configure the exact input-set identifier(s) in `config.json`. For the supplied fixed-input pipeline, an empty pipeline-scoped input set can be created in the YAML editor. Do not use another pipeline's input set.

```sh
# HARNESS_API_KEY supplied securely through the environment
python agent.py execute --config config.json --yes
# Use execution_id printed by execute:
python agent.py status --config config.json --execution EXECUTION_ID
```

Execution submission is asynchronous. `status` returns success only when Harness reports `Success`; Running, Failed and unknown statuses exit nonzero. The execute command does not reconfigure the imported service/pipeline: import updated pinned release YAML in Harness before submitting a new release. Never blindly retry an ambiguous network failure; check execution history for an already-created execution.


## Tests and CI

```sh
python -m unittest discover -s tests -v
docker build -t aks-pilot-sample sample
docker run --rm --read-only --cap-drop ALL --security-opt no-new-privileges -p 127.0.0.1:8080:8080 aks-pilot-sample
# In another terminal: curl -fsS http://127.0.0.1:8080/
```

CI runs configuration/security/command-boundary tests on Python 3.10, 3.12 and 3.13 and builds/runs the sample in a restricted Docker container. CI never uses Azure or Harness credentials. Tests mock external commands/APIs; they do not prove a customer deployment works.

## Optional manual GitHub staging workflow

`Deploy reviewed staging release` is manual-only. Before enabling it, configure a **staging** GitHub Environment with required reviewers and no self-approval, restrict allowed branches, and supply environment variable `AGENT_CONFIG_JSON` containing the reviewed complete configuration. The workflow runs tests and renders it before submission. Never store credentials in this JSON.

Supply environment secret `HARNESS_API_KEY` with pipeline-execute permission. The workflow submits the existing imported Harness pipeline and reports its execution ID; inspect Harness/status for rollout completion. It does not bootstrap a delegate or import entities.

Before deployment submission, the agent fetches the configured Git commit using your existing Git credential helper and verifies that `deploy/app/` contains only `application.yaml`, exactly matching the generated release (including the image digest). This guards against stale or mismatched source. Private Git access must therefore work from both the CLI runner and the deployment engine. Adapt the generator and tests together when extending the supported workload.
